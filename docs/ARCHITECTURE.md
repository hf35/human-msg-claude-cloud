# Архитектура

Этот документ описывает, **как** устроена система. Что она делает и какие
правила соблюдает, описано в [`CLAUDE.md`](../CLAUDE.md). Если документы
расходятся, правила продукта в `CLAUDE.md` главнее, а этот документ нужно
обновить.

## 1. Принципы

1. **Модульный монолит.** Один репозиторий и один серверный процесс. Внутри —
   независимые модули (`api`, `bot`, `worker`), каждый запускается отдельной
   функцией. При росте их можно разнести по разным процессам без переписывания.
2. **Вся бизнес-логика в ядре.** API, бот, бэкофис и воркер только вызывают
   команды ядра. Ядро ничего не знает об HTTP, WebSocket и Telegram.
3. **Данные — единственный источник правды.** Все сроки (дедлайны, паузы,
   время жизни) хранятся полями в таблицах. Таймеров в памяти нет: воркер
   периодически находит просроченные записи.
4. **Инварианты защищает БД.** Правила, которые можно нарушить гонкой,
   закреплены ограничениями и индексами PostgreSQL, а не только кодом.
5. **Доставка не теряется.** События пишутся в outbox в той же транзакции, что
   и изменение данных, и отправляются с повторами.
6. **Минимум инфраструктуры.** Только Node.js и PostgreSQL. Без Redis и брокеров
   сообщений, пока сервер один.

```
│  └────┬─────┘   └──────┬────────┘   └────┬─────┘   └────┬──────┘   │

│                                  ▼                                 │

│  │  → Telegram          │             │                            │
│  └──────────────────────┘             │                            │
└───────────────────────────────────────┼────────────────────────────┘
                                        ▼

```

- **core** — команды предметной области (раздел 6). Каждая команда — одна
  транзакция.
- **api/web** — REST и WebSocket для веб-клиента.
- **api/backoffice** — REST для бэкофиса, отдельная авторизация.
- **bot** — обработчики Telegram-апдейтов, переводят их в команды ядра.
- **worker** — сканер сроков и очереди (раздел 8).
- **delivery** — диспетчер outbox, доставляет события в каналы (раздел 9).

## 4. Структура репозитория

```
apps/
  server/            # точка входа: собирает модули и запускает их
    src/
      api/web/       # REST + WebSocket для пользователей
      api/backoffice/# REST для бэкофиса
      bot/           # grammY: команды, обработчики, клавиатуры
      worker/        # сканер сроков и очереди
      delivery/      # диспетчер outbox, слушатель NOTIFY, адаптеры ws и telegram
      server.ts      # startServer: собирает и запускает все модули
      main.ts        # точка входа процесса: конфиг, сигналы, остановка
  web/               # SPA пользователей (React + Vite)
  backoffice/        # SPA бэкофиса (React + Vite + Refine)
packages/
  core/              # команды ядра, правила, выбор получателя
  db/                # схема Drizzle, миграции, клиент
  shared/            # zod-схемы API, типы событий, тексты (ru, en)
docs/
  ARCHITECTURE.md
docker-compose.yml
```

Правила зависимостей:
- `packages/core` зависит только от `packages/db` и `packages/shared`.
- `apps/server` зависит от всех пакетов; модули внутри него не импортируют
  друг друга, только `core`.
- `apps/web` и `apps/backoffice` зависят только от `packages/shared`.

## 5. Модель данных

Все времена хранятся как `timestamptz` в UTC. Текущее время для правил берётся
из БД (`now()`), а не из Node.js, чтобы не зависеть от расхождения часов.

### Таблицы

**`users`**
- `id`, `channel` (`web` | `telegram`), `google_sub`, `telegram_id`
- `alias` — анонимный псевдоним на языке пользователя при регистрации, уникален
  (если сочетание занято, добавляется число: «Зелёный Кролик 2»)
- `locale` — язык интерфейса и уведомлений (`ru` | `en`)
- `is_test` (пул тестовых пользователей), `is_staff`
- `receiving_enabled` — выключен ли режим «не беспокоить»
- `missed_deadlines` — сколько дедлайнов подряд пропущено (Telegram); ответ или
  «пропустить» обнуляют, при `AUTO_DND_AFTER_MISSED` включается «не беспокоить»
- `bot_blocked_at` — когда Telegram сообщил о блокировке бота
- `cooldown_until`, `last_seen_at`, `created_at`
- Уникальность: `google_sub`, `telegram_id`.

**`web_connections`** — открытые WebSocket-соединения веб-пользователей
- `id`, `user_id`, `server_id`, `connected_at`
- Пользователь веба доступен, если у него есть хотя бы одна запись. При
  старте сервер удаляет записи со своим `server_id`.

**`questions`**
- `id`, `author_id`, `text`, `status` (`queued` | `assigned` | `answered` |
  `expired`), `created_at`, `expires_at`, `answered_at`

**`answers`**
- `id`, `question_id`, `author_id` (тот, кто ответил), `text`, `created_at`
- Уникальность: `question_id` — один ответ на вопрос (правило 4).

**`assignments`**
- `id`, `question_id`, `receiver_id`, `assigned_at`, `deadline_at`,
  `reminded_at`, `ended_at`, `outcome` (`answered` | `timed_out` | `skipped` |
  `reported` | `undeliverable`; `NULL` — назначение активно)

**`blocks`** — исключения по жалобам
- `author_id`, `receiver_id`, `reported_by`, `question_id`, `created_at`
- Первичный ключ: (`author_id`, `receiver_id`).

**`settings`** — продуктовые настройки из бэкофиса (ключ → значение).

**`outbox`** — события для доставки (раздел 9)
- `id`, `user_id`, `type`, `payload` (jsonb), `created_at`, `attempts`,
  `next_attempt_at`, `delivered_at`, `last_error`

**`sessions`** — сессии веба и бэкофиса
- `id` (случайный токен, хранится хеш), `user_id` или `admin`, `expires_at`

### Ограничения, которые защищают правила

| Правило | Как защищено в БД |
|---|---|
| 3. У получателя не больше одного вопроса | Частичный уникальный индекс `assignments(receiver_id) WHERE outcome IS NULL` |
| У вопроса не больше одного активного назначения | Частичный уникальный индекс `assignments(question_id) WHERE outcome IS NULL` |
| 2. Один вопрос — один ответ | Частичный уникальный индекс `questions(author_id) WHERE status IN ('queued','assigned')` |
| 4. Ответ — отдельная запись | `answers.question_id` уникален и ссылается на `questions` |
| 6. Повторно вопрос не назначается | Уникальный индекс `assignments(question_id, receiver_id)` |
| Псевдонимы уникальны | Уникальный индекс `users(alias)` |

Если две параллельные транзакции попытаются нарушить правило, одна из них
получит ошибку уникальности. Ядро перехватывает её и повторяет попытку с другим
получателем или возвращает отказ.

### Индексы для частых запросов

- `questions(created_at) WHERE status = 'queued'` — очередь FIFO.
- `assignments(deadline_at) WHERE outcome IS NULL` — сканер дедлайнов.
- `questions(expires_at) WHERE status = 'queued'` — сканер истечения.
- `users(cooldown_until)` — сканер окончания пауз.
- `outbox(next_attempt_at) WHERE delivered_at IS NULL` — диспетчер.

## 6. Ядро: команды

Каждая команда — одна транзакция. Внутри она блокирует нужные строки
(`SELECT … FOR UPDATE`), проверяет правила, меняет данные и пишет события в
outbox. Если транзакция откатилась, события тоже не появятся.

| Команда | Кто вызывает | Что делает |
|---|---|---|
| `handleIncomingText(userId, text)` | api, bot | Порядок проверок из `CLAUDE.md`: формат → ответ → ожидание → лимит → новый вопрос |
| `submitAnswer(userId, text)` | через `handleIncomingText` | Блокирует активное назначение, проверяет, что оно ещё активно (правило 7), создаёт `answers`, закрывает назначение и вопрос, ставит паузу, пишет событие автору |
| `askQuestion(userId, text)` | через `handleIncomingText` | Проверяет правила 2 и 10, создаёт вопрос, пробует назначить (раздел 7), иначе оставляет в очереди |
| `skip(userId)` | api, bot | Закрывает назначение как `skipped`, ставит паузу, возвращает вопрос в очередь и пробует назначить следующему |
| `report(userId, target)` | api, bot | Жалоба на ответ или на вопрос: пишет `blocks`; для вопроса закрывает назначение как `reported` без паузы |
| `setReceiving(userId, enabled)` | api, bot | Режим «не беспокоить» |
| `markUndeliverable(userId)` | delivery | Правило 11: помечает пользователя, снимает назначение как `undeliverable` |
| `markReachable(userId)` | bot | Пользователь снова написал боту: сбрасывает `bot_blocked_at` |
| `connect / disconnect(userId, connId)` | api/web | Учёт WebSocket-соединений; при подключении пробует назначить вопрос из очереди |
| `staffAnswer(questionId, text)` | api/backoffice | Ответ на `expired`: создаёт служебного пользователя со случайным псевдонимом, создаёт ответ, переводит вопрос в `answered` |
| `sendAsTestUser(testUserId, text)` | api/backoffice | Вызывает `handleIncomingText` от имени тестового пользователя |
| `tick()` | worker | Один проход сканера (раздел 8) |

Команды бэкофиса проходят через те же правила, что и команды пользователей.

## 7. Назначение вопросов

### Подходящий получатель (правило 6)

Один SQL-запрос отбирает пользователей, которые:
- в том же пуле, что и автор, не служебные и не автор;
- доступны: для веба — есть запись в `web_connections`; для Telegram —
  `receiving_enabled` и `bot_blocked_at IS NULL`;
- не заняты: нет активного назначения;
- не на паузе: `cooldown_until IS NULL OR cooldown_until <= now()`;
- не получали этот вопрос раньше;
- нет записи в `blocks` с (`author_id` = автор, `receiver_id` = кандидат).

Из подходящих выбирается **случайный** (`ORDER BY random() LIMIT 1` — при
размерах пет-проекта этого достаточно). Кандидат блокируется
`FOR UPDATE SKIP LOCKED`, чтобы параллельная транзакция выбрала другого.

### Два направления назначения

1. **Новый вопрос ищет получателя** — сразу при создании вопроса.
2. **Освободившийся пользователь ищет вопрос** — когда пользователь подключился,
   выключил «не беспокоить», у него закончилась пауза или снова стал доступен
   Telegram. Берётся **самый старый** подходящий вопрос из очереди (FIFO),
   блокировка `FOR UPDATE SKIP LOCKED`.

Оба направления используют одну функцию проверки, поэтому правила не
расходятся.

### Сроки при назначении

- `deadline_at = now() + ANSWER_TIMEOUT` — полный срок, даже если время жизни
  вопроса закончится раньше.
- Истёкший вопрос (`expires_at <= now()`) не назначается.
- Значения настроек читаются в момент назначения и записываются в поля, поэтому
  изменение настроек не влияет на уже идущие сроки.

## 8. Воркер (сканер)

Раз в `WORKER_INTERVAL` (по умолчанию 5 секунд) воркер выполняет проход. Каждый
шаг обрабатывает записи пачками, каждая запись — в своей транзакции с
`FOR UPDATE SKIP LOCKED`.

1. **Дедлайны:** активные назначения с `deadline_at <= now()` → `timed_out`,
   пауза `COOLDOWN_SKIP`, вопрос возвращается в очередь, событие «время
   истекло» получателю. Для Telegram-пользователя растёт `missed_deadlines`; при
   `AUTO_DND_AFTER_MISSED` включается «не беспокоить».
2. **Напоминания:** активные назначения с
   `deadline_at - ANSWER_REMINDER <= now()` и `reminded_at IS NULL` → событие
   «осталось 5 минут», заполняется `reminded_at`.
3. **Истечение:** вопросы `queued` с `expires_at <= now()` → `expired`, событие
   автору «никто не успел ответить».
4. **Очередь:** для вопросов в очереди ищутся подходящие получатели. Сюда же
   попадают пользователи, у которых только что закончилась пауза.

Шаги идемпотентны: повторный проход ничего не сломает. Задержка срабатывания —
до `WORKER_INTERVAL`, для сроков в десятки минут это неважно.

## 9. Доставка событий

### Outbox

Ядро пишет события в `outbox` в той же транзакции, что и изменение данных.
Типы событий:

| Событие | Кому | Содержание |
|---|---|---|
| `question.assigned` | получателю | текст вопроса, псевдоним автора, дедлайн |
| `question.queued` | автору | «ищем, кто ответит» |
| `answer.received` | автору | текст вопроса **и** ответа, псевдоним ответившего |
| `assignment.reminder` | получателю | сколько осталось |
| `assignment.expired` | получателю | время на ответ истекло |
| `question.expired` | автору | никто не успел ответить |
| `receiving.auto_disabled` | получателю (Telegram) | пропущено слишком много дедлайнов подряд, «не беспокоить» включён автоматически |
| `message.rejected` | отправителю | причина отказа (лимит, ожидание ответа, формат) |

### Диспетчер

- Забирает недоставленные события (`FOR UPDATE SKIP LOCKED`) и отправляет их в
  канал пользователя.
- **WebSocket:** если у пользователя есть открытые соединения, событие
  отправляется во все. Если соединений нет, событие считается доставленным:
  веб-клиент при подключении загружает актуальное состояние через REST.
- **Telegram:** отправка через Bot API. В тихие часы — с
  `disable_notification: true`. Ошибка 403 «бот заблокирован» →
  `markUndeliverable`. Временные ошибки (сеть, 429) → повтор с растущей паузой
  (`next_attempt_at`). Лимиты Telegram (около 30 сообщений в секунду) соблюдает
  плагин grammY для троттлинга.
- Чтобы не ждать следующего прохода, ядро после коммита делает
  `NOTIFY outbox` (`pg_notify` внутри транзакции: при откате уведомления нет), а
  диспетчер слушает `LISTEN outbox` на отдельном соединении и по каждому
  уведомлению запускает проход сразу (`wake()`; уведомления, пришедшие во время
  прохода, сливаются в один следующий проход). Если соединение оборвалось,
  слушатель переподключается и после этого один раз будит диспетчер: события,
  записанные за время обрыва, не ждут периодического прохода. Периодический проход
  остаётся страховкой.

Повторы: после ошибки адаптера `attempts` растёт, а `next_attempt_at` сдвигается
на 5 с, 10 с, 20 с … (не больше 15 минут). После 8 неудачных попыток (или сразу,
если событие нельзя прочитать из таблицы) диспетчер отказывается от события: ставит
`delivered_at`, чтобы оно больше не бралось, а причина остаётся в `last_error`.
Доставка одного события ограничена по времени (15 с), потому что строка заблокирована
на всё время работы адаптера. Каналы без адаптера пропускаются: их события ждут в
таблице. Код выбора и пометки событий живёт в ядре (`dispatchOutbox`), цикл и адаптеры
каналов — в `apps/server/src/delivery`.

Доставка «как минимум один раз»: при сбое событие может прийти повторно.
Клиенты различают события по `id` и игнорируют дубли.

## 10. Доступность пользователей

- **Веб:** при открытии WebSocket создаётся запись в `web_connections`, при
  закрытии удаляется. Соединение проверяется ping/pong; зависшие соединения
  закрываются. После подключения ядро пробует назначить вопрос из очереди.
- **Telegram:** доступен, пока `receiving_enabled` и бот не заблокирован.
  `last_seen_at` обновляется для статистики, на доступность не влияет.

## 11. API

### Веб (`/api`)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/google` | Принимает ID-токен Google, создаёт сессию (httpOnly cookie) |
| `POST` | `/auth/logout` | Завершает сессию |
| `POST` | `/auth/dev` | Только `NODE_ENV=development` и `DEV_LOGIN=true`: вход по имени без Google |
| `GET` | `/me` | Профиль: псевдоним, состояние (ждёт ответа, занят, пауза), лимит |
| `GET` | `/state` | Текущий назначенный вопрос и свой вопрос в ожидании |
| `POST` | `/messages` | Входящий текст → `handleIncomingText` |
| `POST` | `/assignment/skip` | Пропустить вопрос |
| `POST` | `/reports` | Жалоба на вопрос или ответ |
| `GET` | `/history` | Свои вопросы с ответами и свои ответы одной лентой, новые сверху. Пагинация по курсору: `?limit=20&cursor=…`, в ответе `nextCursor` (`null` на последней странице) |
| `GET` | `/ws` | WebSocket: события из раздела 9 |

Отказы возвращаются как `{ "error": "<код>" }` с кодом причины: `empty`,
`tooShort`, `tooLong`, `notText` (400), `awaitingAnswer` (409), `dailyLimit`
(429); для пропуска и жалоб — `no_active_assignment`, `not_answered` (409),
`not_found` (404); для неверного запроса — `invalid_request` (400), без сессии —
`unauthorized` (401). Тело `POST /reports`: `{"target":"question"}` (жалоба на
вопрос, назначенный сейчас) или `{"target":"answer","questionId":"…"}`.

Отдельный `POST /messages` вместо разных эндпоинтов «спросить» и «ответить»
нужен, чтобы порядок проверок был один для всех каналов. Интерфейс при этом
может показывать разные кнопки.

### Бэкофис (`/admin/api`)

- `POST /login`, `POST /logout` — логин и пароль из переменных окружения,
  отдельная сессия.
- `GET /users`, `GET /users/:id` — пользователи и их история.
- `GET /questions?status=…` — вопросы с назначениями и ответами.
- `GET /questions/expired`, `POST /questions/:id/staff-answer` — журнал
  вопросов без ответа и ответ на них.
- `GET/POST /test-users`, `POST /test-users/:id/messages`,
  `POST /test-users/:id/skip` — тестовые пользователи.
- `GET/PUT /settings` — продуктовые настройки.
- `GET /stats` — доля `expired`, количество вопросов и ответов.

Контракты (запросы, ответы, события WebSocket) описываются zod-схемами в
`packages/shared` и используются и сервером, и фронтендами.

## 12. Аутентификация

- **Веб:** фронтенд получает ID-токен через Google Identity Services, сервер
  проверяет подпись и `aud`, находит или создаёт пользователя по `google_sub` и
  выдаёт сессию в httpOnly-cookie (`SameSite=Lax`, `Secure` в production).
  Cookie содержит случайный токен, в БД хранится только его хеш, поэтому
  подпись не нужна. WebSocket авторизуется той же cookie.
- **Бэкофис:** логин и хеш пароля задаются переменными окружения. Отдельная
  cookie с отдельным путём, ограничение частоты попыток входа.
- **Telegram:** пользователь определяется по `telegram_id` из апдейта. В режиме
  webhook запросы проверяются секретным заголовком Telegram.

## 13. Telegram-бот

- `/start` — регистрация, выдача псевдонима, краткие правила.
- `/stop` и `/resume` — режим «не беспокоить».
- `/help` — справка.
- Любой текст → `handleIncomingText`. Не текст → отказ «поддерживается только
  текст».
- Под назначенным вопросом — кнопки «Пропустить» и «Пожаловаться». Под
  полученным ответом — кнопка «Пожаловаться».
- В разработке — long polling, в продакшене — webhook.

## 14. Фронтенды

- **Веб:** вход через Google; один экран с полем ввода, текущим входящим
  вопросом (с таймером, кнопками «Пропустить» и «Пожаловаться») и статусом своего
  вопроса; история. Данные через TanStack Query, обновления через WebSocket. При
  переподключении состояние перечитывается через `GET /state`.
- **Бэкофис:** Refine + Ant Design поверх `/admin/api`. Типовые страницы
  (пользователи, вопросы, настройки) — ресурсы Refine. Журнал вопросов без
  ответа и действия тестовых пользователей — собственные страницы.
- Отдельные сборки: код бэкофиса не попадает в публичный бандл.

## 15. Конфигурация

Переменные окружения (секреты и инфраструктура):

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение к PostgreSQL |
| `PUBLIC_URL` | Внешний адрес сервиса |
| `GOOGLE_CLIENT_ID` | Проверка ID-токенов Google; без него вход через Google выключен (`POST /api/auth/google` отвечает 503) |
| `DEV_LOGIN` | `true` добавляет `POST /api/auth/dev` — вход без Google для разработки. Работает только при `NODE_ENV=development`; в другом режиме сервер не стартует |
| `TELEGRAM_BOT_TOKEN` | Токен бота |
| `TELEGRAM_MODE` | `polling` или `webhook` |
| `TELEGRAM_WEBHOOK_SECRET` | Проверка запросов от Telegram |
| `BACKOFFICE_LOGIN`, `BACKOFFICE_PASSWORD_HASH` | Вход в бэкофис |
| `WORKER_INTERVAL` | Период сканера, секунды (по умолчанию 5) |
| `DISPATCH_INTERVAL` | Период страховочного прохода диспетчера, секунды (по умолчанию 5); `NOTIFY` будит его раньше |
| `SERVER_ID` | Имя сервера в `web_connections` (по умолчанию `server-1`); при старте сервер удаляет свои строки. Постоянное между перезапусками, разное у одновременно работающих серверов |
| `HOST`, `PORT`, `LOG_LEVEL`, `NODE_ENV` | Адрес и порт HTTP (`127.0.0.1:3000`), уровень логов pino, режим |

Продуктовые настройки (сроки, паузы, лимиты, тихие часы) хранятся в таблице
`settings` и описаны в `CLAUDE.md`. Ядро читает их с коротким кешем (несколько
секунд), чтобы изменения из бэкофиса применялись без перезапуска.

## 16. Тестирование

- **Юнит-тесты** для чистых функций: проверка формата, тихие часы, расчёт пауз,
  генерация псевдонимов.
- **Интеграционные тесты ядра** на настоящей PostgreSQL (testcontainers). Это
  основной слой: каждое правило из `CLAUDE.md` и порядок проверок.
- **Тесты гонок:** параллельные `askQuestion` не дают одному получателю двух
  вопросов; ответ одновременно с таймаутом обрабатывается ровно одним способом.
- **Время** в тестах управляется через БД (функция «сейчас» подменяется), чтобы
  проверять дедлайны без ожидания.
- **API** тестируется через `fastify.inject`, бот — через подмену Bot API.

## 17. Развёртывание

- **Локально:** `docker compose up` поднимает PostgreSQL; сервер и фронтенды
  запускаются в режиме разработки; бот работает через long polling.
- **Продакшен:** VPS с Docker Compose:
  - `caddy` — HTTPS (Let's Encrypt), раздаёт статику веба и бэкофиса,
    проксирует `/api`, `/admin/api`, `/ws` и webhook бота;
  - `server` — один контейнер с api, bot, worker и delivery;
  - `postgres` — с volume и ежедневным `pg_dump` во внешнее хранилище.
- Миграции применяются при деплое отдельной командой до запуска нового сервера.
- Бэкофис можно дополнительно закрыть на уровне Caddy (по IP или basic auth).

## 18. Наблюдаемость

- Структурированные логи pino с `requestId`, `userId` и `questionId`.
- `GET /health` — проверка процесса и подключения к БД.
- Статистика для бэкофиса считается запросами к БД: доля `expired`, среднее
  время до ответа, число пропусков и жалоб, размер очереди.

## 19. Путь масштабирования

Пока один сервер, ничего из этого не нужно. Когда понадобится:

1. Разнести `api`, `bot` и `worker` по отдельным процессам — код уже разделён.
   Сканер и диспетчер безопасны при нескольких экземплярах благодаря
   `SKIP LOCKED`.
2. Несколько экземпляров `api`: соединения уже хранятся в БД с `server_id`;
   события между экземплярами передаются через `LISTEN/NOTIFY` (или Redis
   pub/sub при большой нагрузке).
3. Выбор случайного получателя через `ORDER BY random()` заменить на
   более дешёвую выборку, если пользователей станет очень много.
