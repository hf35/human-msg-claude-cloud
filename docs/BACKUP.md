# Бэкапы и восстановление

Сервис `backup` из `docker-compose.prod.yml` каждый день в `BACKUP_AT` (по UTC, по умолчанию
03:00) делает `pg_dump` базы и кладёт дамп в каталог `BACKUP_DIR` на сервере (по умолчанию
`./backups` рядом с compose-файлом). Дампы старше `BACKUP_KEEP_DAYS` (по умолчанию 14) удаляются.

- Формат дампа — custom (`pg_dump --format=custom`), файлы называются `humanmsg-ГГГГММДД-ЧЧММСС.dump`.
- Каждый дамп сразу проверяется (`pg_restore --list`); нечитаемый дамп не сохраняется, а в логе
  появляется строка `FAILED`.
- Ротация идёт только после успешного бэкапа: если база недоступна, старые дампы не стираются.
- Скрипты: [`deploy/backup.sh`](../deploy/backup.sh) и [`deploy/restore.sh`](../deploy/restore.sh).

Все команды ниже выполняются на сервере в каталоге с репозиторием. Сокращение:

```sh
alias dc='docker compose -f docker-compose.prod.yml --env-file .env'
```

## Проверка, что бэкапы идут

```sh
dc logs --tail 20 backup      # строки «backup: created …» раз в сутки
ls -lh backups/               # свежий файл ненулевого размера
```

Сделать бэкап прямо сейчас (например, перед обновлением):

```sh
dc run --rm backup /deploy/backup.sh once
```

## Копия вне сервера

Дампы на том же диске, что и база, не защищают от потери сервера. Регулярно копируйте каталог
`backups/` в другое место, например с вашего компьютера или из cron:

```sh
rsync -a --delete user@server:/path/to/human-msg/backups/ ./human-msg-backups/
```

(или `rclone sync` в облачное хранилище). Дампы содержат переписки пользователей: храните их
так же закрыто, как саму базу.

## Восстановление

`restore.sh` заменяет всё содержимое базы данными из дампа. Это одна транзакция: если
восстановление не удалось, база остаётся как была.

### Из бэкапа в рабочую базу (после аварии или порчи данных)

```sh
# 1. Остановить приложение, чтобы оно не писало в базу во время восстановления
dc stop caddy server

# 2. Восстановить (подставьте имя нужного файла из backups/)
dc run --rm backup /deploy/restore.sh /backups/humanmsg-20261010-030000.dump

# 3. Запустить приложение
dc start server caddy
```

Дамп содержит и журнал миграций, поэтому схема после восстановления соответствует дампу. Если
сервер новее дампа, при обновлении (`dc up -d --build`) недостающие миграции применит сервис
`migrate`.

### На новый сервер

1. Развернуть стек по [инструкции](DEPLOY.md) с теми же `.env`, но пока запустить только базу:
   `dc up -d postgres`.
2. Положить нужный дамп в каталог `backups/`.
3. Выполнить шаг 2 из предыдущего раздела, затем `dc up -d --build`.

### Проверить дамп, не трогая рабочую базу

Восстановить в отдельную пустую базу и посмотреть данные:

```sh
dc exec postgres createdb -U humanmsg restorecheck
dc run --rm -e PGDATABASE=restorecheck backup /deploy/restore.sh /backups/humanmsg-20261010-030000.dump
dc exec postgres psql -U humanmsg -d restorecheck -c 'select count(*) from users'
dc exec postgres dropdb -U humanmsg restorecheck
```

Проверять восстановление стоит не реже раза в месяц: бэкап, который ни разу не восстанавливали,
может оказаться непригодным.
